# AnaesthesiaCore → Base44 cutover: slice 1 (admin session and role)

Date: 23 November 2026
Branch: `migrate-base44-runtime` (isolated from `main`, no production changes)
Status: **staged, opt-in, default off**. Production stays on Lovable Cloud.

This slice implements the smallest independently testable piece of the runtime
move: an admin-only session whose identity and role are verified by a Base44
backend function. Nothing else changes runtime — no data is copied, no role is
granted, no billing, domain, secret, backend configuration or deployment is
touched, and every existing Supabase path is byte-for-byte the production path
when the opt-in flag is absent.

### Request flow

```
browser (Base44 bearer token)
   └─ POST /functions/adminSession        (SDK functions.invoke)
        └─ createClientFromRequest(req).auth.me()   ← identity from the token only
             └─ user.role === BASE44_ADMIN_ROLE ?    ← server-side role only
                  200 { authenticated, isAdmin, userId }
```

* `401` → signed out, `403` → disabled account, `503` → deployment has not
  configured `BASE44_ADMIN_ROLE`, `200 { isAdmin: false }` → access denied.
* The granting role name is **deployment configuration**, not a constant. When
  it is unset every caller is refused; there is no default role name, no
  user-id list, no e-mail allowlist and no shared admin code anywhere.
* The function reads no request body, so a caller cannot claim a role.
* Responses are `Cache-Control: no-store`.

### Enabling it (staging only)

```bash
VITE_BASE44_ADMIN_SESSION=1
VITE_BASE44_APP_ID=<base44 app id>
# Base44 function environment:
BASE44_ADMIN_ROLE=<role configured in the Base44 app settings>
```

Without `VITE_BASE44_APP_ID` the gate shows "Base44 admin sessions are enabled
but VITE_BASE44_APP_ID is missing" and grants nothing. Unsetting the flag
restores the Supabase gate exactly, with no cleanup needed.

This sandbox has **no Base44 credentials**, so the live end-to-end path (real
Base44 app, real admin account) is not verified here; the boundary, the guard
and every UI state are covered by tests, and the default (flag-off) path is
verified in the running app.

slice does not modify it; the relay's assertion/JWKS/replay safeguards stay as

**Base44 app `6aac4e437f1bfbc772befee2` (native Anaesthesiacore) could not be
inspected from this environment** — no credentials, no authorized connector, and
no import path into another app. No claim is made about its schema, auth mode or
data. Comparing it is a prerequisite for the data-migration slice, not for this

## 3. Concrete blockers for the cutover

1. **Recoverable export.** The production Lovable backend is paused and this
   environment holds no service-role credential, so no schema dump, row export or
   storage listing can be produced here. Needed: an owner-run export (schema +
   data + storage objects) from a restored/readable copy of the project, checksums
   and row counts recorded with it, a restore rehearsal into a disposable
   project, and an explicit retention/deletion decision for that copy. Until then
   no migration can be validated, only inventoried.
2. **Account identity.** Supabase `auth.users` (UUIDs, password hashes, OAuth
   identities, MFA state) cannot be copied into Base44. Base44 user ids are
   different values. Migration needs an explicit, reviewed
   `auth.users.id → Base44 user id` map plus a chosen re-authentication route
   (Base44 invitation + forced password reset, or OAuth re-link), and a decision
   on accounts whose e-mail is an Apple private relay address. E-mail is a join
   hint only: it is mutable, shared on some devices, and never proof of identity.
   The local-first progress caches (`anaesthesia-core-*`, `…-cloud-migrated:<id>`)
   also mean a changed identity can silently drop or double-count progress.
3. **Roles.** `user_roles` must be re-created as Base44 user roles with an audited
   manual assignment step by the app owner. `BASE44_ADMIN_ROLE` must be set per
   environment; this slice deliberately has no default and no shared code.
4. **Private support correspondence.** `support_tickets` / `support_messages` are
   account-scoped private conversations (owner/admin RLS). Bulk copying them needs
   an explicit privacy decision, a lawful basis and a retention period; they must
   not be used as a test fixture.
5. **Progress merge semantics.** Progress is local-first with cloud upsert; the
   cutover must decide last-write-wins vs union per table and prove no tick is
   lost or duplicated across a dual-run period.
6. **Storage.** Podcast audio (public) and lighthouse reports (private) need
   object-level copies and access-rule parity; podcast rows reference exact
   original files and clinical holds, so object identity must be preserved.
7. **Functions and scheduled work.** 28 Deno edge functions, 7 of them
   unauthenticated by design (`verify_jwt = false`) — each needs a per-function
   port and an auth-parity review. The three `pg_cron` + `net.http_post` jobs have
   no configured Base44 equivalent yet.
8. **Payments.** `donations` / `donation_clicks` and `paypal-webhook` are out of
   scope; billing must not change.

**Sandbox preview data calls.** The committed `.env` still points at the Lovable
project host `aqkusdwwhlqqttvnxuwu.supabase.co`, which now answers `NXDOMAIN`
(checked with a public resolver on 23 November 2026). A fresh preview load
therefore logs three failed requests — `functions/v1/log-visit`,
`rest/v1/home_announcement`, `rest/v1/reviews` — and the announcement banner,
public reviews and visitor logging cannot be exercised in this environment.
Those failures predate this slice (the commit touches no Supabase call site, no
data hook and no `.env` value) and come from the paused backend, not from the
Base44 boundary; they clear when the data slice points these reads at a reachable
store. The pages themselves render and handle the failures without unhandled
exceptions.

### Bundled Apple apps

* Native sign-in is **not implemented** for a packaged `capacitor://` origin
  (`docs/native-iphone-setup.md`). Base44 session storage and any OAuth return
  path need an approved hosted-auth or custom-scheme callback before a build can
  rely on Base44.
* Needs device testing for: session persistence across app restarts, token
  refresh, sign-out, loss of network, and the App Review test account.
* Needs an App Store privacy-manifest and disclosure update before shipping a
  build that contacts a second backend.
* Bundled content must keep working offline; Base44 must not become a hard
  dependency for reading topics.
